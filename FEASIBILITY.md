This is the initial research and design record. The implemented v0.1.0 scope is documented in [README](README.md), the final local model in [estimation](docs/ESTIMATION.md), and the subsequent non-SK source and endpoint research in [providers](docs/PROVIDERS.md). Future proposals below, including weather, background provider refresh and accuracy studies, are not claims of shipped functionality.

Research date 2026-09-03. This document distinguishes observed behavior from proposed app design. The reference component was inspected at commit `320513798301d491e3984fae8bb1a1cede22e8c0`.

**The app is feasible, with Busan as the first supported provider.** Historical bills can supply a seasonal baseline, while occasional physical meter readings correct the current estimate and teach the model about recent consumption. No sensor, Home Assistant installation, or continuously running server is needed for that calculation. The main ongoing engineering cost is maintaining provider connections. Forecast accuracy is a separate question that requires actual household observations.

**An authorized live read-only test succeeded.** Using the supplied temporary credentials through the reference component's HTTP client, the probe discovered one contract and parsed all 13 months advertised by its billing page. No browser or Home Assistant runtime was used. Credentials were entered through hidden process input and remained in memory. An explicit request-path allowlist excluded submission endpoints. Saved results contain structural findings and coverage dates, without credentials, account identifiers, addresses, bills, or meter values.

**The existing component provides a useful starting point.** Its `portal.py` separates HTTP retrieval and parsing from Home Assistant. Its `model.py` and `sensorless.py` contain calculation logic without network or Home Assistant dependencies. The current sensorless algorithm maps today's date to last year's usage period, divides volume by the actual number of days, and blends this with a recent physical-reading rate. This is already close to the proposed product. Port the logic and preserve its source attribution when creating a native app. The repository has an MIT license. [Reference source](https://github.com/mahlernim/ha-busan-city-gas/tree/320513798301d491e3984fae8bb1a1cede22e8c0/custom_components/busan_city_gas), [license](https://github.com/mahlernim/ha-busan-city-gas/blob/320513798301d491e3984fae8bb1a1cede22e8c0/LICENSE).

**Regional reuse is promising within SK E&S.** Public GET requests checked both `www.skens.com` and `ebpp.skens.com` for eight regional login pages. All 16 returned HTTP 200 and the same whitespace-normalized `checkLoginForm` function hash. Each used `id`, `pw`, `returnURL`, a relative `loginProcess.do` endpoint, and success code `S`. The public caloric-query pages also exposed the same `call_EBPP_044.do` request shape across the eight portals. These are concrete indicators of shared implementation, but they do not prove identical authenticated billing responses or shared user accounts.

The reproducible public audit is saved in `research/provider-public-audit.json`, with its script beside it. Public entry points include the [Busan login](https://www.skens.com/busan/login/login.do) and [Cowon login](https://www.skens.com/koone/login/login.do).

A reusable SK connector must parameterize more than the URL. The current code embeds Busan's `C000` company identifier in contract identities, billing requests, and caloric-factor validation. Company codes, tariff categories, response differences, and account linkage need verification per provider before enabling it for users. Treat every other SK provider as a candidate until a legitimate account can read its contract, latest bill, and historical bills correctly.

**A national app needs several provider connectors.** Seoul City Gas exposes a different `/front/member/Login` route and its homepage has a contract-number-based simple query. Yesco uses `/login.view`, an independently implemented `/loginChk.json` login request, and a separate monthly-bill route. Its public login source contains a reCAPTCHA verification branch, so uninterrupted headless login cannot be assumed. An interactive challenge would need the supported provider flow. Public inspection alone did not establish authenticated access to these services. [Seoul City Gas](https://www.seoulgas.co.kr/), [Yesco login](https://www.lsyesco.com/login.view).

Region selection should narrow the provider list, then confirm the provider or ask for a district when needed. Seoul and Gyeonggi contain several providers, and some districts are split. Busan can default to 부산도시가스. Preserve a direct provider chooser for users who know their supplier. Do not confuse 전북에너지서비스 with 전북도시가스. [KOGAS provider and supply-area directory](https://www.kogas.or.kr/site/koGas/1020408040000).

**Suggested first-use flow.** Select region, confirm provider, enter provider credentials, choose a linked contract if there are several, import the latest bill and available history, then confirm today's physical meter reading. The latest bill can establish a dated initial anchor if the meter matches, but a fresh physical reading gives a better start. Show current results as soon as the latest bill arrives and fetch older bills progressively. The read-only test results are recorded separately in `research/busan-read-only-results.json`.

Provide direct links for account recovery and registration. Busan's recovery page is [아이디/비밀번호 찾기](https://www.skens.com/busan/login/find.do), and its login page offers member and guest verification flows. Account recovery in a browser does not automatically sign the app in. The user returns to the app with the recovered credentials. New residents may also need the provider to link their supply contract. [Official login](https://www.skens.com/busan/login/login.do).

**Use the 13-, 12-, and 11-month history as seasonal shape.** In September 2026 these correspond roughly to August, September, and October 2025. However, a bill labeled September may describe gas consumed across August and September. Store each bill's usage start and end, raw meter volume, corrected volume or energy, meter identity, tariff information, and provenance as separate fields. Do not derive the seasonal curve from money or confuse corrected billing volume with the physical meter's register.

Fetch all available useful history, ideally at least 14 months and up to 24 initially, instead of requesting only three billing labels. This accommodates billing lag and adjacent usage periods. For a first model, use the verified usage-per-day values over their actual periods. A later candidate can smoothly interpolate neighboring seasonal rates. If smoothing is introduced, check that it does not create negative rates or materially distort the period totals. Three monthly observations cannot reveal the actual daily pattern.

**Physical checks provide two different improvements.** One check resets the estimated cumulative register to an observed value. Two checks separated in time also reveal consumption over that interval. For example, if a meter rises from 1,200.0 to 1,207.7 in seven days, observed use is 1.1 cubic metres per day. If the seasonal baseline expected 7.0 cubic metres over those same seven days, this household used about 10% more than that baseline. This is an illustrative calculation, not a result from the test account.

A candidate model should compare each observed interval with the seasonal amount integrated over the same interval. Learn a recent household multiplier from these comparisons, giving newer reliable intervals more weight. Start with a conservative pull toward the historical baseline, then let several consistent readings increase the influence of recent behavior. Apply that adjustment to the coming seasonal curve. This preserves the approach of winter or spring while reflecting current use. For near-zero historical consumption, use an absolute recent rate instead of dividing by a tiny baseline.

The current component's fixed 50% maximum recent-data weight is a transparent baseline, not a demonstrated optimum. Its recent rate uses observations separated by 7 to 28 days. It reduces recent influence after 14 days without a physical check and returns to history at 28 days. Repeated household differences may warrant a better learned adjustment, but candidate weights and decay times should be selected through prospective evaluation rather than asserted as accurate. [Current estimator and its documented limitations](https://github.com/mahlernim/ha-busan-city-gas/blob/320513798301d491e3984fae8bb1a1cede22e8c0/docs/estimation.md).

**The proposed calibration controls can remain compact.** Show the cumulative meter estimate prominently with `맞음`, `+0.1`, `-0.1`, and `직접입력`. The prompt should explicitly ask the user to compare it with the physical meter. `맞음` records a physical observation at the displayed precision. Plus and minus edit a draft value, and a final `이 숫자로 확인` records one observation. Tapping a stepper repeatedly must not generate multiple training observations. Direct input should allow the full meter reading.

The current HA notification path deliberately records plus/minus as adjustments rather than physical observations. For the app, a confirmed correction can train the model because its meaning is explicitly a meter check. Dismissing or postponing a reminder supplies no evidence. An old notification should open a fresh comparison screen rather than confirming an estimate calculated hours ago. Preserve valid zero-use intervals, reject accidental decreases, and handle a replacement meter or new home by starting a new sequence. The 0.1 step is an input convenience, not an accuracy promise. [Current notification handling](https://github.com/mahlernim/ha-busan-city-gas/blob/320513798301d491e3984fae8bb1a1cede22e8c0/custom_components/busan_city_gas/coordinator.py#L682).

**Handle incomplete data explicitly.** With only one reading and no history, the app knows the register at that time but cannot infer a credible household consumption rate. With two sufficiently separated readings it can make a provisional short-term projection. A newly linked contract may not provide a year of relevant history. Missing history should offer manual tracking or bill import and explain the limited estimate. A new bill can reconcile the completed period without turning an estimated provider reading into an independently measured observation when its measurement status is unknown.

**Weather is the most useful later addition for heating households.** A seasonal pattern alone cannot anticipate this year's cold spell or a changed heating schedule. Heating degree days provide a physically motivated temperature input. Apply weather adjustment to the heating-sensitive part of demand rather than automatically multiplying cooking and hot-water use by the same factor. This is an extension to validate after the simpler model. [EIA explanation of degree days](https://www.eia.gov/energyexplained/units-and-calculators/degree-days.php).

City-level weather can be fetched without sending billing history or a precise home address. A prototype could use Open-Meteo, whose free hosted API is for noncommercial use. A commercial release needs an appropriate weather-service arrangement. Ordinary users should not need their own API key. Weather outages should leave the local seasonal model usable. [Open-Meteo service terms and plans](https://open-meteo.com/en/pricing).

**A native mobile application fits the local-storage requirement.** My proposed first implementation is Android with Kotlin and Compose. A Flutter application is also a reasonable choice if Android and iOS are both required immediately. Provider HTTP transport, bill parsing, normalized storage, the estimator, and the UI should be separate modules. The Python calculation design is portable, but the HA coordinator and notification integration need replacement in a native app.

Store credentials encrypted using a key protected by Android Keystore, and keep bills and observations in private app storage. On iOS, use Keychain for credentials with device-only settings when local-only storage is promised. Exclude credentials, sessions, and private history from ordinary cloud backups unless the user explicitly opts into an appropriate backup design. Network requests still send credentials to the gas provider for login. They do not need to pass through an app-operated server. Provide disconnect and delete-local-data actions. [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [Apple Keychain](https://developer.apple.com/documentation/security/keychain-services).

A regular website or PWA is a less direct fit for provider integration because cross-origin credentialed reads depend on the provider allowing them. A backend proxy would introduce a service handling account credentials and bills. A native HTTP client avoids the browser CORS dependency, although provider authentication and any interactive challenges still apply. No provider CORS support was verified in this research. [Browser CORS behavior](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

The estimate can be calculated from stored timestamps when the app opens. There is no need to keep incrementing a counter in the background. Fetch bills on opening and with modest background refresh, using cached history when offline. Schedule a weekly local reminder. Android WorkManager supports persistent background work but is not an exact-time scheduler. Reminder wording must tolerate delayed refresh and open the latest estimate. [Android WorkManager](https://developer.android.com/reference/androidx/work/WorkManager.html), [Apple local notifications](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app).

**The home screen should separate facts and forecasts.** Show the current estimated meter reading, estimated use in the current billing period, estimated final period cost, latest confirmed bill, and last physical check. Display the provider's actual billing period rather than silently assuming the calendar month. A usage forecast can work before precise cost forecasting does. Busan's published formula includes volume correction, average heat content, tariff, basic charge, and VAT. Other providers and discounts need their own tariff handling. Future heat factors and rates may remain provisional. [Busan tariff and calculation method](https://ebpp.skens.com/busan/rate/guide.do).

Self-reading submission is a later optional feature. A local calibration should only update local records. Any eventual provider submission needs an explicit separate action and a fresh physical reading. It is not required to demonstrate the usefulness of the estimator.

**There is an existing market, so the product needs a clear focus.** Gasapp already advertises billing, energy management, and AMI-based usage and cost features. Its existence demonstrates that a generic bill viewer is not distinctive. The opportunity worth testing is a quiet, private, hardware-free forecast that learns from a quick weekly check, especially for households outside supported smart-meter services. This investigation did not establish that competitors lack every form of sensorless estimation. [Gasapp's own feature descriptions](https://www.gasapp.co.kr/).

**The first release should be deliberately small.** Support Busan login, contract selection, historical bill import, local storage, initial reading, weekly calibration, estimated meter and billing-period use, provisional cost where supported, and data export. Use one common provider interface from the beginning. Add one other SK provider only after validating it with that provider's account, then decide whether the shared connector generalizes well enough to expand further. Offer manual tracking for unsupported suppliers instead of presenting their login as operational.

**Validate the forecast using predictions saved before corrections.** At every weekly check, retain the previously issued prediction, the physically observed reading, the time interval, and model version. Measure the error before applying the new observation. Compare historical-only, recent-rate-only, the existing HA blend, and the proposed seasonal adjustment over identical future intervals. Otherwise, a graph that resets to the correct value after every check will misleadingly appear accurate.

Evaluate absolute error in cubic metres and bias at seven days, error in projected period use, and cost error separately. Percentage error alone is unreliable for very low summer consumption. Split results by cooking-only and heating households, and include a heating transition. A small pilot of roughly 5 to 10 households over 6 to 8 weeks can reveal usability and connection failures, but broad accuracy claims need more homes and winter observations. These are proposed pilot sizes, not statistical assurances. An optional range around forecasts should be labeled provisional until its coverage has been evaluated.

**The remaining decisions are evidence questions.** Establish the history retained for newly linked and older contracts, whether a second SK account returns compatible bill fields, how often logins require renewed interaction, whether users actually perform weekly checks, and whether the adaptive model improves future estimates over a simple baseline. A successful login and complete monthly history demonstrate data access. They do not by themselves demonstrate daily forecasting accuracy.
